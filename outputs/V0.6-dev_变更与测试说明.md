# 保温试验排程工具 V0.6-dev

## 基线与版本

- 基线：用户指定的 `V0.5.4.1 Stable` 源文件。
- UI 版本：`V0.6-dev`。
- 数据结构版本：`schemaVersion: 6`。
- 当前状态：开发版，等待真实业务数据实测；未升级为稳定版。
- 未开发：云同步、通知、Dashboard；未重构 55℃算法。

## 主要变更

1. 新增独立的 36±1℃长期保温协议，不复用或扩展 55℃ `targetDays 1～14`。
2. 保质期映射：3/6/9/12 个月分别对应 15/30/45/60 天。
3. 业务模型固定为“一次放入、多次取样、最终取出”：只有 Day0 是放入，后续节点不再出现放入。
4. 每 7 天生成一次“取样｜感官/理化”；总周期末生成“取出｜最终感官/理化”。
5. 微生物检查由用户在 Day7～Day14 中选择；与常规取样同日时合并成一次“取样｜感官/理化/微生物”，非 7 天节点时才生成独立取样。
6. 微生物日期未指定时显示“微生物检测日待指定”，不进入操作日程。
7. 全部节点共用一个时间基准：开始前按计划放入时间，Day0 确认后改按实际放入时间；后续原始节点时间=`baseStart + Day×24h`。
8. Day0 即使落在周末也不顺延；后续节点周六顺延两天至周一、周日顺延一天至周一。
9. 尚未完成的节点可单独调整“计划操作时间”；单点调整不改变 Day0 或其他节点，并保留原始节点时间追溯。
   手工选在周末的后续节点仍按协议顺延至周一；Day0 手工选周末仍不顺延。
10. 每项操作独立为“待执行 / 已完成 / 本次不做”，状态只由确认动作改变。
11. 已完成操作在操作日程中只读；撤销完成后清空实际操作时间和数量，保留执行人和备注。
12. 36℃排程结果改为八列：Day、动作、检测项目、状态、计划操作时间、实际操作时间、数量、备注。
13. 操作日程明确显示“36℃｜放入 / 取样 / 取出”，并附检测项目，避免把检测名误解成动作。
14. 36℃逾期仅按“计划操作时间已过且尚未确认完成”判断；调整到未来后立即退出逾期列表。
15. 感官/理化和微生物项目可设为“本次不做”；最终取出节点强制启用。
16. 所有启用操作完成后才能归档；微生物仍待指定时不能归档。
17. CSV 为四个文件：试验清单、55℃排程、36℃排程、操作日程；JSON 完整保留 `protocol36`。
18. 改选微生物检测日会清除旧日期未确认的时间、数量和单点计划调整，保留执行人、备注；已完成时须先撤销。

## 数据结构

项目级 36℃协议：

```json
{
  "protocol36": {
    "modelVersion": 2,
    "totalDays": 60,
    "microDay": 10,
    "targetConfirmed": true,
    "tasks": {
      "sensory-21": { "enabled": false },
      "micro": { "enabled": true }
    }
  }
}
```

36℃任务执行记录使用独立键：`expId|36|taskKey`。

```json
{
  "completeConfirmed": false,
  "actualTime": "",
  "adjustedPlanTime": "2026-10-02T09:30",
  "qty": "",
  "person": "",
  "note": ""
}
```

`taskKey` 包括：`start`、`sensory-7`、`sensory-14`、`micro`、`final` 等。微生物与 7 天节点重合时共用对应的 `sensory-Day` 物理取样记录，不再生成第二条操作。55℃执行记录仍沿用原来的 `expId|day` 与三层时间字段。

## 迁移

- `schemaVersion 5 → 6` 只新增并规范化 36℃协议和任务执行记录。
- 旧 55℃项目的 `targetDays`、目标数量、启用状态、三层时间和实际执行记录不改值。
- 导入旧 JSON 时依次执行旧版兼容迁移，再升级到 schema 6。
- JSON 导出/导入往返保留 `protocol36` 和全部 36℃任务记录。
- 旧 V0.6-dev 若曾为同一 Day 分别保存感官和微生物记录，会合并为一次物理取样记录。若两条旧记录含有不同执行事实，原微生物记录另存为 `legacy-micro-dayN` 审计键，仅在 JSON 中保留，不生成额外操作行。
